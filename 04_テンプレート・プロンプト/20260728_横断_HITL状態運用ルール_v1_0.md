## 1. 目的

積み残しタスクを「自分で進められるもの」と「他者の判断を待っているもの」に機械的に分離し、朝イチ対話および週次棚卸しで判断コストを下げる。

出典資料の中核概念は次の一文である。

> 人間介入を対話入力ではなく状態遷移として扱う

つまり Claude は実行中にその場で確認を求めるのではなく、介入が必要になった時点で状態ファイルを更新して停止し、茂木さんの応答を待って再開する。

---

## 2. HITL状態の定義（4種）

出典ファイルの定義をそのまま採用する。

| 状態 | 意味 | 茂木さん業務での典型例 |
|---|---|---|
| GATE | 人間の承認が必要 | 旧版のBoxミラー方針の確定、版体系の再設計判断 |
| REV | 実装後のレビュー待ち | 生成済みファイルの内容確認、保存結果の確認 |
| QRY | 仕様上の質問・確認 | R10採番の正式性、台帳の要確認セルの値 |
| BLK | 進行不能なブロック | 前提が矛盾しており着手すると破壊が起きる状態 |

### 2-1. 判定順序

判定は上から順に行い、最初に合致したものを採用する。

1. 前提が矛盾していて着手すると既存資産を壊す可能性がある → BLK
2. 他者に事実を問い合わせないと確定しない → QRY
3. 方針の可否を茂木さんが決める必要がある → GATE
4. 成果物は出来ており内容確認だけが残っている → REV
5. いずれにも該当しない → HITL状態を付けず通常タスクとして扱う

### 2-2. BLK と GATE の切り分け

- GATE は「決めれば進む」状態である
- BLK は「決める前に事実確認や再設計が要る」状態である

判断に迷った場合は自律継続せず BLK へ倒す。出典資料の推奨運用ルール7に準拠する。

## 3. 既存ステータス凡例との対応

ブロッカー一元管理には既に5種のステータス凡例が存在する。これを廃止せず、上位概念として HITL状態を重ねる。

| 既存ステータス（ブロッカー一元管理） | 対応するHITL状態 | 備考 |
|---|---|---|
| 期限超過 | QRY または GATE | 依存先への再依頼が必要なら QRY |
| 催促可能 | QRY | 事実待ちのため |
| 待機 | QRY | 次回催促予定日まで待機 |
| プル型 | QRY | 能動的催促をしない受領待ち |
| 依頼予定 | GATE | 依頼するか否かを茂木さんが決める段階 |

既存の5種は「依存先が他者であるブロッカー」に特化しており、自己完結タスクの承認待ち（GATE）や進行不能（BLK）を表現できない。HITL状態を重ねることでこの空白が埋まる。

## 4. ファイル責務の分離

出典資料は3ファイル構成を採るが、茂木さん環境はgitを使用しないため2ファイルに縮約する。

| ファイル | 役割 | 版管理 |
|---|---|---|
| AGENT_STATE.md | ランタイム状態・HITL状態の記録 | 版番号なし・常に上書き |
| 本ルール（20260728_横断_HITL状態運用ルール_vX_Y.md） | 状態定義・判定基準・運用ルール | 版番号あり・旧版へ退避 |

### 4-1. この分離が解く既知の課題

版付き文書内に退避statusを書くと、退避を実行するたびに記述が反転し、再編集と再同期が発生する。2026年7月10日（金曜日）に複数回発生した。

状態を版番号なしのファイルへ切り出すことで、状態が変わっても版上げが不要になる。出典資料が AGENT_STATE.md を gitignore 対象としているのは同じ理由である。

### 4-2. 遵守事項

- 版付き文書には HITL状態を書かない
- 版付き文書は前版番号を中立に指すのみとする
- 物理所在および退避statusはファイル管理台帳で一元管理する（既存方針を継続）

## 5. AGENT_STATE.md の記載項目

| 列 | 内容 |
|---|---|
| ID | BLK-01 / GATE-01 のように状態プレフィックスと連番 |
| HITL状態 | GATE / REV / QRY / BLK |
| 件名 | 1行で内容がわかる表現 |
| 対象 | 対象ファイル名または施策ID |
| 依存先 | 待っている相手。自己完結なら「自己」 |
| 記録日 | YYYY/MM/DD |
| 解除条件 | この条件が満たされたら状態を解除できる、という記述 |
| 根拠 | 出典ファイル名または実体照合の実行結果 |

「根拠」列は必須とする。宣言だけでなく確認の実行結果を残すという出典資料の方針に準拠する。

---

## 6. 状態の解除と記録

1. 解除条件が満たされたら、該当行を「解除済み」セクションへ移動する
2. 解除日と解除方法を記載する
3. 行は削除しない（旧版削除禁止の運用思想と整合させる）

---

## 7. 運用への組み込み

| タイミング | 実施内容 |
|---|---|
| 朝イチ対話 Step 3 | AGENT_STATE.md の QRY 行のみを催促候補として抽出する |
| 朝イチ対話 締めくくり | GATE 行が2件以上ある場合は本日の判断枠として提示する |
| 週次棚卸し | BLK 行の解除条件が進展したか確認する |
| 月次振り返り | 状態別の平均滞留日数を集計する |

朝イチ対話プロンプトv3.0の事前準備#3は「ブロッカー一元管理.md を読み込み」と記載されている。AGENT_STATE.md を追加参照する改訂は、本ルールの運用1週間後に判断する。現時点では改訂しない。

## 8. 適用範囲と対象外

### 適用する

- 積み残しタスクの分類
- 版上げ着手前の可否判定
- 他者依存タスクの催促管理

### 当面適用しない

- 個別施策の進捗管理（既存の施策別台帳が担う）
- 資料の版管理（ファイル管理台帳が担う）
- カレンダー実績登録（既存ルールが担う）

出典資料も初期段階では対象を限定することを推奨している。範囲を広げるのは運用が安定してからとする。
