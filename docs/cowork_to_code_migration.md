# Cowork のスケジュールタスクを CODE へ移す検討と実測結果

作成日 2026/09/14（JST）

## 用語統一表

| 正式表記 | NG表記 | 備考 |

| Cowork | コワーク、CoWork | スケジュールタスクの従来の実行環境 |

## 2. 実施した移行

### 2.1 問い合わせ分析ダッシュボード 週次生成（火曜10時）

スキル inquiry-dashboard は同期スキルとして CODE 側にも配られているため、
スクリプトをリポジトリへ複製していない。複製すると版が二重になるためである。
リポジトリには CODE 側の実行と出口検査だけを置いた。

- `jobs/inquiry_dashboard/run.sh` 生成と検査を通す
- `jobs/inquiry_dashboard/verify_dashboard.py` 出口検査を機械判定にする

実測結果（実データで確認、2026/09/14）。

```

合格 回帰確認 simple        基準日2026-08-31 期待223件 実際223件
合格 再現性 analysis        2回生成してバイト一致
合格 再現性 simple          2回生成してバイト一致
合格 個人情報 analysis      検出なし

合格 件数整合 MARKET        config 12件が分析版に入っている
合格 旧版にMARKET無し        旧版は市場動向を持たないのが正しい
合格 件数整合 CONTENTS      config 0件が分析版に入っている

```

指示書に書かれた出口検査のうち、機械判定できる項目はすべて自動化した。
CONTENTS の供給元は現在空であり、その場合 Content Gap の判定は「判定不可」になる。
これは不具合ではなく、供給元の状態をそのまま反映したものである。

未解決の制約が1つある。生成物の Box 配置である。

- Box Drive の同期フォルダは CODE のコンテナに存在しない
- Box への直接HTTPSは遮断されている
- コネクタの `upload_file` はテキスト内容を引数で渡す方式であり、
  分析版のHTMLは約337KBある。この大きさを引数で渡す運用は現実的ではない

したがって、当面は次のいずれかになる。判断は人が行う必要がある。

1. 生成と検査を CODE で行い、成果物を会話経由で受け取って Box へ置く（人手が1回入る）
2. 生成と検査を CODE で行い、Box 配置だけを Cowork 側に残す
3. Box 配置の自動化は見送り、CODE では検証用途に限って使う

### 2.2 工数集計 月次レポート（毎月2日9時）

- `jobs/kousuu_shukei/aggregate_kousuu.py` 集計とレポート生成
- `jobs/kousuu_shukei/test_aggregate_kousuu.py` 回帰テスト28件

判定の分かれ目になった実例を回帰テストに固定した。
件名「【済】DWP2_資料作成_会議アジェンダ12枚と競合調査総括報告8枚」は、
件名全体を走査すると資料作成と会議の2語に該当するが、
作業種別は第2トークンの資料作成である。この判定順序をテストで守る。

実データでの確認（2026年8月分、2026/09/14 実行）。

- 取得したイベント 240件
- 集計対象（件名が【済】で始まるもの）49件、合計 50時間38分
- 要確認 36件（すべて採番ルールに合わない施策ID。対象月が採番規則の適用前のため想定内）
- 8語に当てはまらない件名 0件、複数該当 0件、所要時間が取れない件名 0件

このタスクは Cowork 側でまだ一度も実行されていない（`last_run` の記録が無い）。
初回を CODE で組む方が手戻りが小さいと考えられる。

### 2.4 問い合わせCSV 毎朝更新

- `jobs/inquiry_csv/merge_inquiry_csv.py`
- `jobs/inquiry_csv/test_merge_inquiry_csv.py` 回帰テスト21件

メール本文から会社名や製品を読み取る工程は機械にできないため、スクリプトの外に置いた。
スクリプトが担うのは、重複判定（発生日・客先・製品・宛先アドレスの組）、

実データの複製で往復を確認した（2026/09/14）。

- 取得開始日の算出は 2026-09-08（台帳の最新日 2026-09-10 の2日前）

なお、この確認はスクラッチ領域の複製に対して行い、Box 上の台帳は変更していない。

## 3. 移していないもの、およびその理由

| スケジュールタスク | 判断 | 理由 |
|---|---|---|
| ファイル管理台帳の週次バージョン棚卸し | 移行不可 | Projects のドキュメント読み出しに依存しており、CODE からは使えない |
| FY26 TODO照合 本体（毎朝5時） | 保留 | 長時間実行と保存未達が環境の変更だけで解消するという根拠が無い。単独で検証すべき |
| FY26 TODO照合 欠落検知・週次完走率 | 保留 | 移行可能だが効果は中。本体の扱いが決まってから合わせて動かす方が整合する |
| 議事メモ雛形、公開コンテンツ鮮度点検、モーニングブリーフ | 移さない | 判断と文章生成が本体であり、スクリプト化できる部分が小さい |
| 調査系5件 | 移さない | Web調査と要約が本体。スクリプト化の余地が小さい |
| 一時ファイル月末整理リマインド | 移さない | リマインドが主目的であり、効果が限定的 |

## 4. Routine を CODE へ移す手順

1. 対象の Routine を Cowork 側で無効にする（削除しない。切り戻せるようにする）
2. CODE 環境（`env_018Vn3RidJiDubEoadwZzWVT`、Default、trusted network access）を
   指す Routine を新規に作る。毎回まっさらなセッションで動かす設定にする
3. 新しい Routine のプロンプトには、次の3点を必ず書く
   - このリポジトリを clone し、該当ジョブのテストを先に走らせること
   - コネクタで取得したデータをファイルへ落とし、スクリプトへ渡すこと
   - 数値はスクリプトの出力をそのまま使い、文章を書くときに数え直さないこと
4. 1回目は並走させない。移行前後で二重に成果物が作られる事故を避ける
5. 2回から3回動かして結果が安定してから、Cowork 側の Routine を削除するか判断する

## 5. この検討の限界

- コネクタの疎通は確認したが、Cowork と CODE で同じ権限範囲かどうかまでは検証していない。
  共有設定に依存するフォルダを扱う場合は、移行時に対象フォルダ単位で確認する必要がある
- ネットワークポリシーは環境の設定であり、変更されれば Box への直接通信の可否も変わる。
  本書の記載は 2026/09/14 時点の実測である
- Cowork 側の所要時間と CODE 側の所要時間を同条件で比較していない。速くなるとは書けない
- 移行によって減るのは「毎回の解釈のぶれ」であり、判断が要る工程の手間ではない
